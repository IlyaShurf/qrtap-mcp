# Скилл: приём заявок на запись и их обработка

## Задача

Принимать заявки на запись с публичной страницы и разбирать их: посмотреть новые, связаться
с человеком, отметить решение. Работает как простая входящая очередь без CRM и без ежедневника.

## Когда применять

- Мастер или салон принимает записи через Instagram и телефон, и половина теряется.
- Нужен способ оставить заявку с QR на визитке или витрине.
- Заявок немного (единицы-десятки в день), полноценная система записи избыточна.

## Что важно понимать сразу

**Платформа не уведомляет гостя.** Ни при подтверждении, ни при отказе SMS и письмо не
уходят. Статус в QRTap — это внутренняя отметка бизнеса о принятом решении. Позвонить
человеку всё равно нужно, и ассистент обязан говорить об этом прямо, а не создавать
впечатление, что клиент уже оповещён.

**Заявка — это персональные данные.** В ответе приходят имя и телефон реального человека.
Использовать их можно только для обработки самой заявки: не переносить в сторонние сервисы,
не собирать в списки для рассылок, не показывать там, где они не нужны.

**Время не разбирается.** Поле `preferred_at` — свободный текст ровно в том виде, как его
написал гость: «завтра после 14:00», «в субботу утром». Платформа его не парсит и в календарь
ничего не кладёт.

## Что понадобится

- `QRTAP_API_KEY` ([где взять](https://app.qrtap.kg/workspace/api)).
- Публичная страница — см. [скилл про страницу специалиста](stranica-specialista.md).
  Форма заявки живёт на ней; список услуг из `services` подсказывает гостю, на что писаться.

## Шаги

### 1. Подготовить страницу

Заполните `services` — гость выбирает услугу из этого списка, и заявки становятся разборчивее:

```
qrtap_update_page(slug = "<slug>", content = { ...весь объект..., "services": [
  {"name": "Маникюр с покрытием", "price": "1500 сом"},
  {"name": "Педикюр", "price": "2000 сом"}
]})
```

Помните: `content` перезаписывается целиком. Сначала `qrtap_get_page(slug)`, затем правка,
затем запись.

Если запись ведётся во внешнем сервисе, вместо формы можно указать `bookingUrl` — тогда
гость уйдёт туда, и заявки в QRTap приходить не будут.

### 2. Сделать QR на страницу

```
qrtap_create_code(url = "<public_url>", title = "Запись, витрина", external_ref = "zapis-vitrina")
```

### 3. Смотреть входящие

Новые — статус `new`:

```bash
curl -s -H "Authorization: Bearer $QRTAP_API_KEY" \
  "https://app.qrtap.kg/api/v1/bookings?status=new"
```

Через MCP: `qrtap_list_bookings(status = "new")`.

В ответе по каждой заявке: `id`, `service`, `preferred_at`, `guest_name`, `guest_phone`,
`status`, `created_at`. Без статуса вернутся все заявки — удобно для обзора за период.

Полезная форма для человека — короткий список, отсортированный по времени поступления:

```bash
curl -s -H "Authorization: Bearer $QRTAP_API_KEY" \
  "https://app.qrtap.kg/api/v1/bookings?status=new" \
| python3 -c "
import json,sys
for b in json.load(sys.stdin)['data']:
    print(f\"{b['created_at'][:16]}  {b['guest_name']:<15} {b['guest_phone']:<15} {b['service']:<25} {b.get('preferred_at','—')}\")
"
```

### 4. Обработать заявку

Порядок именно такой:

1. Ассистент показывает пользователю заявку целиком: услуга, желаемое время, имя, телефон.
2. Пользователь решает — подтвердить или отказать. **Решение принимает человек.**
3. Человек звонит гостю и договаривается.
4. Только после этого статус фиксируется в системе.

```bash
curl -s -X POST "https://app.qrtap.kg/api/v1/bookings/$BOOKING_ID/status" \
  -H "Authorization: Bearer $QRTAP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"status": "confirmed"}'   # или "declined"
```

Через MCP: `qrtap_set_booking_status(bookingId, status)`.

Вернуть заявку в `new` нельзя — статус меняется в одну сторону. Если ошиблись, вторая
попытка проставит другой конечный статус, но исходное «новое» состояние не вернётся.

### 5. Разобрать очередь целиком

Разумный порядок для ассистента, когда заявок накопилось:

```
1. qrtap_list_bookings(status = "new")
2. Показать пользователю все заявки одним списком, старые сверху
3. Дождаться решений по каждой — одним сообщением, не по одной
4. Для каждой: qrtap_set_booking_status(...)
5. Показать итог: подтверждено N, отказано M, и напомнить, что звонить нужно самому
```

Не проставляйте статусы «по смыслу»: похожая на спам заявка, странный телефон, неудобное
время — это всё поводы спросить, а не решить самому.

### 6. Посмотреть, что было

```bash
curl -s -H "Authorization: Bearer $QRTAP_API_KEY" \
  "https://app.qrtap.kg/api/v1/bookings?status=confirmed"
curl -s -H "Authorization: Bearer $QRTAP_API_KEY" \
  "https://app.qrtap.kg/api/v1/bookings"          # все
```

Сколько людей вообще дошло до страницы — по сканам кода:

```bash
curl -s -H "Authorization: Bearer $QRTAP_API_KEY" \
  "https://app.qrtap.kg/api/v1/codes/$CODE_ID/stats?from=2026-07-01T00:00:00Z"
```

Сканы против числа заявок за тот же период — это и есть конверсия витрины в запись.

## Как проверить результат

1. **Форма работает.** Оставить тестовую заявку на своей странице и найти её в
   `?status=new`.
2. **Поля на месте.** В заявке есть `service`, `guest_name`, `guest_phone`; `preferred_at`
   совпадает с тем, что вводили.
3. **Статус фиксируется.** После вызова заявка исчезает из `?status=new` и появляется в
   `?status=confirmed` или `?status=declined`.
4. **Ничего не потеряно.** Число заявок без фильтра равно сумме по трём статусам.
5. **Гостю ничего не ушло.** Проверить на тестовой заявке со своим номером: сообщений нет —
   это ожидаемое поведение, а не сбой.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| Заявки не приходят | На странице задан `bookingUrl` | Убрать его, если запись должна идти через QRTap |
| Гость не получил подтверждения | Платформа не шлёт уведомлений | Позвонить; предупредить об этом пользователя заранее |
| Статус проставился не тот | Вернуть в `new` невозможно | Проставить верный конечный статус и отметить это при звонке |
| В списке пусто | Фильтр `status=new`, а всё уже обработано | Запросить без фильтра |
| `404` при смене статуса | Неверный `id` заявки | Взять `id` из свежего `GET /api/v1/bookings` |
| Пропали услуги на странице | `PATCH` с частичным `content` | Читать перед записью, отправлять объект целиком |
